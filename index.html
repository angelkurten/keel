The context layer for the agents inside your product

Keel turns your product's events into one graph per customer that remembers what was true and when. Every agent you build reads it through the same five tools, over MCP, HTTP or a typed SDK, so you stop rebuilding the pipeline for each one.

cartridges/jira/cartridge.yamlYAML
entities:
  issue:   { ref: issues.id }
  project: { ref: projects.key }
relations:
  blocks: { from: issue, to: issue }
events:
  issue.status_changed:
    subject: issue
    payload: { status: string, status_category: [new, indeterminate, done] }
rules:
  blocked:
    applies_to: issue
    definition: "Blocked while an issue that blocks it is not done."
    when:
      all:
        - { not: { predicate: status_category, eq: done } }
        - { via: blocks, direction: in, any: { not: { predicate: status_category, eq: done } } }
memory:
  ttl: { tenant: never, task: 14d, agent: 1d }
  requires_evidence: [global, tenant]
  evidence: [event]   # an event this tenant's log applied to the same subject

Four agents shouldn't mean four pipelines

Every new agent repeats the same work: extract the customer's data, decide what "blocked" or "at risk" means, keep its own memory. Keel does it once, from your events.

Without KeelN pipelines

Each agent has its own pipeline, its own rules and its own memory.

With Keelone layer

One deterministic ingest. Every agent reads the same graph through the same five tools.

How it works

  1. Send your events

    From Postgres CDC, an outbox, Kafka, SQS, webhooks or the SDK.

  2. Declare a cartridge

    Your entities, events and rules in YAML, plus ten-line handlers. Typed SDKs come out of it.

  3. Keel builds the graph

    One bitemporal graph per tenant. No LLM in ingest; replay gives the same graph.

  4. Agents read five tools

    context, history, search, related, annotate. Rules arrive evaluated.

rules

Define "blocked" once. Every agent gets the verdict.

Rules live in the cartridge, not in prompts. Keel evaluates them over the whole graph, so the model receives the answer instead of working it out from raw facts.

  • 26 points more right on whole-project rule questions with both GPT-6 Luna and Claude Haiku 5.5.
  • Fewer tokens: 77k against 149k a question with Luna, 60k against 78k with Haiku.
  • Rules compose: all, any, not, follow relations with via, measure durations.

bitemporal

Know what was true, and when you knew it

Every fact carries when it was true and when Keel learned it. Late events and corrections close facts instead of overwriting them, so an agent can audit what another agent saw when it decided.

  • as_of and as_known_at on every read.
  • Deterministic replay: the same log gives the same graph, in any arrival order.
  • Provenance on every fact: source, evidence, who corrected it.

memory

Memory with scopes, enforced by the layer

Agents write what they learn with annotate. The cartridge says who may write which scope, how long it lives and what counts as evidence. The prompt can't talk its way past it.

  • 0% of answers repeat a poisoned write with Keel's checks (the evidence check as fixed after the run), against 91–98% without.
  • 0 leaks in 26,666 random reads across tenants, scopes and agents.
  • One graph per tenant: no tool can return another tenant's facts.

sdk

Your cartridge, as a typed client in your language

keel sdk writes one file for your product's repo, the way protoc does: a type per event payload, a constructor per event, subject helpers, the rules, and a client for the five tools. Your compiler catches a payload that drifts from the catalog before Keel ever sees it.

  • TypeScript, Python, Go and PHP, each with a small published runtime and tested end to end against keel serve.
  • --check in CI fails the build when the cartridge moves on and the generated file is stale.
  • One contract: the same cartridge drives ingest, the tools and every client.
$ keel sdk typescript cartridges/jira -o src/keel-jira.ts
import { client, emit, subjects } from "./keel-jira";

const keel = client({ baseUrl, tenant: "spring", agent: "triage" });

await keel.events([emit.issueStatusChanged({
  tenant: "spring", subject: subjects.issue("SPR-142"),
  occurredAt: new Date(), source: "jira",
  payload: { status: "Blocked", status_category: "blocked" },
})]);   // ✗ Type '"blocked"' is not assignable to
        //   '"new" | "indeterminate" | "done" | null'

const ctx = await keel.context(subjects.issue("SPR-142"));
ctx.evaluation.blocked;   // true
$ keel sdk python cartridges/jira -o app/keel_jira.py
from app import keel_jira as kj

keel = kj.client("http://keel.internal:8000", "spring", secret=SECRET, agent="triage")

Running in three commands

An example cartridge and its events ship with the repository. Point Claude Code, Codex or any MCP client at it.

  1. Install

    Python 3.10+, or run the container.

    git clone https://github.com/angelkurten/keel
cd keel && pip install keel-context

  2. Validate and load

    Check the events against the cartridge, then build the graph.

    keel validate examples/fleet \
  --events examples/fleet/events.jsonl
keel ingest examples/fleet \
  examples/fleet/events.jsonl

  3. Serve the five tools

    Over MCP for your agent, or HTTP for your backend.

    claude mcp add keel -- keel serve \
  examples/fleet --tenant acme-logistics \
  --events examples/fleet/events.jsonl
